## 4. Findings

### High

#### H-1 — Retrying an expired AutoLaris instruction erases the old transaction id; a late payment cannot be reconciled **[run]**

- **Where:** `src/lib/autolaris-payment.ts:586-600` (reuse `UPDATE`), reached
  from `src/pages/api/order-status.ts:76-101` (buyer "Buat ulang").
- **What is wrong:** once `expires_at` passes, the row reads `expired` and the
  buyer may regenerate. The same `payment_transactions` row is rewritten with
  a new `reference_id` and `provider_transaction_id = NULL`, then the new
  `trx_id` is stored. The module's own rationale for
  `AUTOLARIS_EXPIRED_RECHECK_HOURS = 24` (`:367-373`) is that a QRIS/VA "can be
  paid in the last minute and settle at the provider after this side has
  already marked it expired" — but that recheck only asks about the *stored*
  id, which is now the new one. The `UPDATE` also has no status guard
  (`WHERE id = ?` only), so concurrent retries each create a provider
  instruction and only the last id survives.
  ```sql
  UPDATE payment_transactions SET reference_id = ?, ..., status = 'pending', ...,
    provider_transaction_id = NULL, ... WHERE id = ?
  ```
- **Evidence:** scratch script on the full migrated schema, real functions:
  ```
  after retry pending 887702 [{ id: 1, provider_transaction_id: 'TRX-2', ... }]
  hourly Advice will ask about: [ 'TRX-2' ] (TRX-1, the paid one, is gone)
  manual confirm with TRX-1 -> PAYMENT_MISMATCH
  admin PATCH paid -> Pembayaran online hanya boleh ditandai paid oleh rekonsiliasi AutoLaris.
  ```
- **Impact:** buyer's money is received but the order can reach `paid` by no
  path (Advice, manual reconciliation, admin PATCH): never dispatched, never
  reported as Purchase, and the buyer is likely asked to pay again.
- **Suggested fix:** keep every attempt's provider id (an attempts table, or a
  `previous_provider_transaction_id` included in the Advice sweep and accepted
  by manual confirm); make the reuse `UPDATE` conditional
  (`AND status IN ('failed','expired')`, check `changes`); optionally run one
  Advice inquiry on the old id before regenerating.
- **Owner:** `ARCHITECTURE.md` (payment section), `UNIMPLEMENTED_SPECS.md`;
  `RELEASE.md` if a migration is added.

### Medium

#### M-1 — An ambiguous Mengantar outcome is treated as a rejection; a re-push can create a second shipment **[read]**

- **Where:** `src/lib/mengantar-dispatch.ts:510-516` → `recordDispatchError`
  (`:193-208`); client timeout 10 s (`src/lib/mengantar-client.ts:262`, `:443-445`).
- **What is wrong:** a fetch timeout and an HTTP 200 whose body fails
  `parseMengantarDispatchResponse` (`src/lib/mengantar-order.ts:288-304`) both
  land in the generic `catch`, which clears `provider_dispatch_claimed_at` and
  the `DISPATCHING` marker:
  ```ts
  `UPDATE orders SET provider_dispatch_error = ?, provider_dispatch_claimed_at = NULL,
     shipping_status = 'pending' WHERE id = ? AND provider_order_id IS NULL ...`
  ```
  `MENGANTAR_INTEGRATION_SPEC.md` §5C states the same behaviour and lists
  "retry behavior that cannot duplicate pickup creation" as remaining work.
- **Impact:** if Mengantar accepted the shipment before the timeout, the order
  is immediately pushable again; for COD that is two parcels and two COD
  collections for one order.
- **Suggested fix:** split outcomes into *rejected* (4xx / `success:false`) and
  *unknown* (timeout, network, unparseable 200); on unknown keep the order
  blocked with a distinct marker (e.g. `DISPATCH_UNKNOWN`) until an operator
  check or a lookup by order number.
- **Owner:** `MENGANTAR_INTEGRATION_SPEC.md` §5C.

#### M-2 — Delete and void ignore a live payment instruction and an in-flight dispatch **[read]**

- **Where:** `src/lib/order-lifecycle.ts:359-374` (delete guard), `:384-395`
  (deletes `payment_transactions` with the order).
- **What is wrong:** the guard refuses only
  `payment_status IN ('paid','settled','success') OR provider_order_id IS NOT NULL`.
  A QRIS/VA order whose instruction is `pending` (or `expired` inside the 24 h
  recheck window) is deletable together with its transaction row, and so is an
  order with `provider_dispatch_error = 'DISPATCHING'`. Voiding by PATCH has the
  same blind spot: `PENDING_AUTOLARIS_INQUIRY_SQL` requires
  `stock_restored_at IS NULL`, so a voided order's instruction is never asked
  about again.
- **Impact:** a buyer who pays after the delete leaves money with no local
  record; a shipment accepted during the dispatch window is orphaned
  (`mengantar-dispatch.ts:440-490` finds no row to persist into).
- **Suggested fix:** refuse delete while a live/recently expired instruction or
  a fresh dispatch claim exists; keep voided orders' instructions in the Advice
  sweep and alert if one turns up paid.
- **Owner:** `ARCHITECTURE.md` (order lifecycle), `UNIMPLEMENTED_SPECS.md`.

#### M-3 — Google Ads offline conversions are queued for void (cancelled) paid orders **[run]**

- **Where:** `src/lib/google-ads-offline.ts:302-315`
  (`reconcileGoogleAdsConversions`).
- **What is wrong:** for non-COD orders the query checks only
  `payment_status IN ('paid','settled','success')`; it ignores
  `shipping_status IN ('cancelled','returned')` and `stock_restored_at`. The
  lifecycle allows a paid transfer/QRIS order to move to shipping `cancelled`
  with payment still `paid` (`order-lifecycle.ts:150-200`). The Meta leg has the
  guard (`paid-order-purchase.ts:94`, `isVoidOrder`, prior audit finding 1);
  the Google leg does not. The cron is hourly (`wrangler.jsonc:67`), and a
  backfill from `startAt` picks up every historical void order.
- **Evidence:** order `manual_transfer / paid / cancelled`, `stock_restored_at`
  set, with a `gclid`:
  ```
  queued: 1 [ { order_number: 'INV-1', qualification: 'online_paid', status: 'pending' } ]
  ```
- **Impact:** refunded/cancelled sales are reported to Google Ads as
  conversions, inflating ROAS and training bidding on non-revenue.
- **Suggested fix:** add `AND o.stock_restored_at IS NULL AND o.shipping_status NOT IN ('cancelled','returned')`
  (or reuse `STOCK_RELEASED_SQL`) to the reconcile query, and re-check before
  the drain sends; add a test next to the existing reconcile test.
- **Owner:** `docs/GOOGLE_ADS_SETUP.md`, `TRACKING_SPECS.md`.

#### M-4 — A failed schema upgrade kills the whole hourly cron, including its heartbeat **[read]**

- **Where:** `src/worker.ts:39` — `await ensureSchemaUpgraded(env.OMS_DB);`,
  outside the `housekeeping` wrapper.
- **What is wrong:** `ensureSchemaUpgraded` throws `SchemaUpgradeError`
  (`src/lib/schema-version.ts:358-381`); every later step is skipped, including
  the heartbeat whose comment (`:51-53`) says it is "stamped before any later
  step can fail", AutoLaris Advice reconciliation, both outbox drains and
  `evaluateOperationalAlerts`.
- **Impact:** on a store with no traffic, nobody is alerted (the schema alert
  fires only from middleware on a request); the status panel blames the
  scheduler; paid QRIS/VA orders stop being reconciled.
- **Suggested fix:** stamp the heartbeat first; wrap the schema step and on
  error raise the schema alert from the cron, then skip only schema-dependent
  steps.
- **Owner:** `OBSERVABILITY.md`, `ARCHITECTURE.md` §10.

#### M-5 — Meta CAPI `fetch` has no timeout and is awaited on request paths **[read]**

- **Where:** `src/lib/meta-capi.ts:180` (no `signal`); awaited via
  `deliverCapiEvent` in `src/pages/api/meta-event.ts:210`,
  `src/pages/api/v1/tracking/events.ts:146`, `src/lib/paid-order-purchase.ts:154`.
- **What is wrong:** every other provider client sets a timeout
  (`mengantar-client.ts:412`, `autolaris-client.ts:447`,
  `plugins/kelola/sync.ts:107`, `operational-alerts.ts:127`); this one does not.
- **Impact:** a slow Graph API stalls the browser tracking response and the
  admin paid confirmation; the sequential drain (`capi-outbox.ts:384`) can
  exceed its 5-minute lease and send a row twice.
- **Suggested fix:** `signal: AbortSignal.timeout(5_000)` at `meta-capi.ts:180`.
- **Owner:** `TRACKING_SPECS.md`, `OBSERVABILITY.md`.

#### M-6 — Two hourly cron queries scan the whole `orders` table **[run]**

- **Where:** `src/lib/rts-scoring.ts:150-163` (receiver-score backfill) and
  `src/lib/google-ads-offline.ts:302-315` (reconcile).
- **What is wrong:** `EXPLAIN QUERY PLAN` on the full chain gives `SCAN orders`
  for both. The backfill filters on `receiver_performance_checked_at IS NULL`,
  `date(created_at) >= date('now','-30 days')` and `json_extract(...)` — none
  index-usable; the reconcile scans every order since `startAt` when the outbox
  already holds them all.
- **Impact:** ≈ 24 × order-count rows read per day per query (≈ 2.4 M/day each
  at 100k orders) against the D1 Free 5 M/day read allowance. Each runs only
  when its integration is configured.
- **Suggested fix:** bound both by a bare `created_at >= ?` (ISO string) so
  `idx_orders_created_at` serves it; add a partial index
  `ON orders(id) WHERE receiver_performance_checked_at IS NULL` in a forward
  migration.
- **Owner:** `ARCHITECTURE.md` (data layer).

#### M-8 — Admin status change is validated on a stale read and written unguarded; a void order can be reactivated **[run]**

- **Where:** `src/pages/api/admin/orders/[id].ts:745-766` (status-only PATCH,
  `UPDATE orders SET ... WHERE id = ?`); same shape in the bulk path
  `src/lib/order-lifecycle.ts:301-310`.
- **What is wrong:** the transition is validated against the row read at the
  start of the request; the write does not re-assert it. `admin/shipping.ts:405-410`
  already does it correctly (`AND shipping_status = ?`).
- **Evidence:** provider sync moves shipped → returned (void); the operator's
  PATCH validated against `shipped` then writes `delivered`:
  ```
  PATCH result: { updated: true, stockRestored: false }
  { shipping_status: 'delivered', stock_restored_at: '2026-10-30T19:37:42.882Z' }
  ```
- **Impact:** breaks the invariant "a released order cannot be reactivated"
  (`order-lifecycle.ts:150-164`); a returned COD order can read as delivered and
  then qualify for Google `cod_delivered` upload.
- **Suggested fix:** bind every lifecycle mutation to the validated state
  (`AND payment_status = ? AND shipping_status = ? AND stock_restored_at IS ?`)
  and treat `changes = 0` as a conflict.
- **Owner:** `ARCHITECTURE.md` (order lifecycle).
