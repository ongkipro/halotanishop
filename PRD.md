## A43 — Resolve kecamatan to Mengantar areas without calling Mengantar

**Status:** Proposed 2026-10-29. Pairs with A42: more origins mean more quotes,
so each quote should spend as little as possible before the rate call.

### What exists today (verified on disk)

- The form searches the bundled 7,285-district index
  (`src/data/indonesia-districts.ts`, Kepmendagri 2025) locally.
- The chosen district + city is resolved to a Mengantar area id through
  `/address/search` (`/api/locations?level=resolve`), cached in **KV for 24
  hours** (`location-cache.ts`); free-text searches are cached in KV for 10
  minutes. Every cache miss is a Mengantar round trip **and a KV write**, the
  scarcest Free-plan resource (ADR-021, PRD A40).
- The rate itself (`estimateRates`) is always live, and submit re-verifies the
  courier, service, cost and weight before the order is written
  (`MENGANTAR_INTEGRATION_SPEC.md`).

### Goals

- Resolving a kecamatan costs no Mengantar call and no KV write once it has
  been resolved anywhere.
- The rate stays live: what the buyer is charged is what Mengantar quotes.

### Non-goals

- Caching or precomputing **rates**. Prices, COD fees and courier coverage
  change; a stored rate would be charged to the buyer and then differ from what
  Mengantar bills at dispatch. Revisit only with A-330's measurement showing
  the rate call is the bottleneck, and then as a short display-only cache that
  submit still re-verifies.
- Replacing the bundled district index or its source.

### Requirements

- **REQ-243** — A resolved district (district + city + province → Mengantar area
  id and label) shall be stored permanently in D1, not for 24 hours in KV, and
  read from there before Mengantar is asked.
- **REQ-244** — A stored area that Mengantar later rejects (a rate or dispatch
  answering "area not found") shall be dropped and resolved again, so a renamed
  or retired area heals itself.
- **REQ-245** — The free-text search cache shall stop writing KV on every
  keystroke prefix; local district search already answers the form.
- **REQ-246** — Optionally, once A-417's data shows area ids are stable, a
  pre-resolved index for all 7,285 districts shall ship with the product, so a
  new install never asks Mengantar to resolve at all.
- **REQ-247** — The resolve result returned to the form shall be byte-identical
  to today's for the same input.

### Technical decisions

- **Recommendation, in order:** (1) a per-install D1 table, keyed by the
  catalogue's own district|city|province triple (the form can only offer
  those, so the key space is the 7,285 catalogue rows), with no expiry,
  replacing the KV write (*amended 2026-10-29:* rows answer for 30 days from
  `resolved_at`, then resolve again, until REQ-244's drop-on-rejection is
  approved as A-415 — a never-expiring row with no drop path would keep a
  wrong id for good; fallback answers are not stored);
  (2) **seed it from the store's order history** in the
  same migration: every past order already carries `destination_area_id` with
  its district, city and province, so each district a store has ever shipped
  to is resolved on day one with no Mengantar call; (3) the same order history,
  read across the 14 databases, is the stability study for the area ids, so it
  can run now instead of after weeks in production; (4) only if ids agree
  across stores, a bundled index for every district (one more value per row of
  the district data, about 100 KB raw), generated by a throttled, approved,
  read-only script, with the D1 table kept as the fallback.
- **Seeding takes the most common id per district.** An order's area can come
  from the operator's precise kelurahan mode (`MENGANTAR_INTEGRATION_SPEC`), so
  one district can carry several ids; the representative the form would
  resolve is the most frequent one among orders that did not use precision
  mode, and the seed records how many orders agreed.
- **Why not a shared Cloudflare database for all stores:** each install is its
  own Worker and D1 (ADR-001); a shared database would be a cross-store
  dependency and a new binding. The bundled index gives every store the same
  data with no binding at all.
- **Protected surface.** `/api/locations` and the location modules are on the
  forms' path. The change is limited to where a resolved area is looked up and
  stored; the response shape is pinned by a test (REQ-247).

## A42 — Multiple warehouses, each quote from the warehouse nearest the buyer

**Status:** Proposed 2026-10-29. **Touches protected surfaces by design**
(shipping quote, the rate and submit routes); each touch is listed and needs
Paduka's approval as its own item before code.

### What exists today (verified on disk)

| Layer | State |
| --- | --- |
| Schema | Already multi: `warehouses` (name, `origin_area_id`, `pickup_address_id`, address, city, province, contact, `origin_label`), `orders.warehouse_id`, `pickup_schedules.warehouse_id`. |
| Settings | `/admin/settings/warehouse` edits **one** warehouse (`save-warehouse` in `api/admin/settings.ts`), with `WarehouseOriginPicker` resolving a precise Mengantar sub-district and `ensurePickupAddress` registering the pickup address at Mengantar. |
| Quote | `shipping-quote.ts` uses `SELECT … FROM warehouses ORDER BY id LIMIT 1`: the first warehouse, whoever the buyer is. |
| Order | Stores `warehouse_id` from the quote (`quote.warehouse?.id`), as do headless checkout and lead conversion. |
| Dispatch and pickup | Already per order: dispatch joins the order's warehouse for `pickup_address_id`; the shipping workspace lists up to 10 warehouses and schedules pickups per warehouse. |
| Location data | The bundled district index has no coordinates; the buyer's district, city and province are known from the form. |

So the order, dispatch and pickup already follow whichever warehouse the quote
returns. The missing pieces are managing several warehouses, and the quote
choosing one by the buyer's location.

### Goals

- An operator keeps several warehouses, each registered at Mengantar, in its own
  settings screen.
- Each quote, and so each order, ships from the warehouse nearest the buyer,
  and the buyer is charged that warehouse's rate.
- A store with one warehouse behaves exactly as today.

### Non-goals

- Splitting one order across warehouses, per-warehouse stock (ADR-023: stock
  never gates a sale), or routing by courier.
- GPS distance. No coordinates exist in the data; IP geolocation is too coarse
  for this and the form already has the buyer's real district.

### Requirements

- **REQ-237** — Pengaturan → Gudang shall list the store's warehouses (at most
  10, matching the shipping workspace) with add, edit, delete and **Jadikan
  utama**. Exactly one is primary.
- **REQ-238** — A warehouse can be saved only with a Mengantar origin resolved
  to a precise sub-district and a pickup address registered at Mengantar
  (`origin_area_id` and `pickup_address_id` both set), and the list shows each
  warehouse's Mengantar status. A warehouse that is not ready is never chosen.
- **REQ-239** — Each warehouse serves a set of provinces, defaulting to its own;
  the operator can add provinces. The quote chooses: (1) a ready warehouse
  serving the buyer's province; (2) else a ready warehouse on the same island
  group; (3) else the primary. Ties go to the primary, then the lowest id.
- **REQ-240** — The quote, the order's `warehouse_id`, the dispatch pickup
  address and the pickup schedule shall all follow that one choice; submit
  re-verifies the rate from the same warehouse it was quoted from.
- **REQ-241** — Re-quoting an existing order from the admin (address edit) shall
  use the order's own warehouse unless the operator changes it.
- **REQ-242** — A store with one warehouse shall get byte-identical quotes,
  orders and dispatches to today's, proven by tests run before and after.
- **REQ-248** — A warehouse with orders cannot be deleted, only made inactive;
  the primary cannot be made inactive.
- **REQ-270** (Must, unwanted; added 2026-10-30 at Paduka's request) — If the
  chosen warehouse is not the primary and its Mengantar rate call fails or
  returns no usable rate, then the quote shall be re-made once from the primary
  (the store's default warehouse), and the order shall record the primary as
  its warehouse. The primary is never retried; when it has no rate either, the
  branch's own error surfaces as before (a COD quote with a city takes the
  city average from the primary). Only a warehouse the quote *chose* is
  swapped: a named one (`warehouseId` — the admin re-quote and its preview,
  REQ-241) fails instead, because the admin save compares no price with its
  preview. Headless checkout, which compares no submitted shipping cost,
  opts out and fails closed.
  - Acceptance: Given a Surabaya branch whose rate call fails, When a Surabaya
    buyer is quoted, Then the rates and `warehouse` are the primary's, a
    `shipping-quote-primary-fallback` warning names both ids, and submitting
    the shown price is accepted.

### Technical decisions

- **Province coverage, not distance (recommendation).** It is deterministic,
  costs no extra Mengantar call, uses data the form already has, and lets the
  operator correct edge cases (a Jawa Barat warehouse serving DKI). Island
  groups are a static map of the 38 province codes.
- **Considered and deferred: cheapest of all warehouses.** Quote every ready
  warehouse in parallel and take the cheapest. Most accurate to "ongkir from
  the nearest", but N Mengantar calls per quote, slower forms and N× the rate
  limit. Revisit after A-330/A43 measure the rate call, as a per-store mode.
- **The protected touches, each its own approval:**
  1. `shipping-quote.ts`: replace the first-warehouse read with the chooser and
     accept `destinationProvince` in `ShippingQuoteInput`.
  2. `/api/shipping-rates`, `/api/v1/geo/shipping-rates`, the three submit
     routes, lead conversion and the admin re-quote: pass the buyer's province
     (or, for a re-quote, the order's own warehouse). The rate route receives
     only the destination id and city today, so the province is derived on the
     server from the bundled district index (city → province) where that is
     unambiguous.
  3. The forms: none, if A-404 shows the server can derive the province; a form
     change is a separate proposal only if it cannot.
- **The chooser is a pure function** in `src/lib/warehouse-choice.ts`, tested
  without D1; the quote only feeds it the ready warehouses.
- **Schema:** `warehouses.is_primary`, `warehouses.is_active` and
  `warehouses.served_provinces` (JSON array of codes) in one forward migration;
  the first existing warehouse becomes primary and serves its own province.

## A41 — Variant weight: required for new products, visible on every order

**Status:** Proposed 2026-10-29. Most of the weight path already exists; this
section closes the gaps and states what it does not change.

### What exists today (verified on disk)

| Layer | State |
| --- | --- |
| Schema | `product_variants.weight_grams integer DEFAULT 1000 NOT NULL` since `0000`. Every variant created without a weight weighs 1000 g; a product with two such variants is 1000 g **each**, not 500 g split. |
| CMS form | `ProductForm.tsx` has a required "Berat (gram)" input per variant, but a new variant row starts prefilled with `1000`, so a new product never has to state its weight. |
| Save API | `product-mutation.ts` turns a missing weight into `1000` (`parseInteger(...) ?? 1000`) and refuses zero or negative values. |
| Shipping quote | `shipping-quote.ts` sends `weight_grams / 1000 × quantity` kg to Mengantar for the rate. |
| Dispatch | `mengantar-dispatch.ts` sends the same per-item weight when it creates the Mengantar order, but reads the variant's weight **at dispatch time**, not the weight that was quoted at checkout. |
| Order detail and invoice | Weight is shown nowhere: not per item, not as an order total. |

### Goals

- A product that is not live yet cannot be saved without an explicit weight
  per variant, because that weight sets the Mengantar shipping cost.
- A live product keeps its stored weight; one that never had one stays at the
  1000 g per variant it already carries.
- The operator sees the weight on the order: per item and in total, in grams
  with the kg beside it.

### Non-goals

- Changing how the quote or the dispatch computes weight. `shipping-quote.ts`
  and `mengantar-*.ts` are protected surfaces (TASKS, *Protected surfaces*).
- Volumetric weight, package dimensions, or per-courier rounding.
- Rewriting live stores' weights. The 1000 g default stays the rule for live
  data; operators correct individual products in the CMS.

### Requirements

- **REQ-230** — Weight is stored per variant in whole grams. Live variants keep
  their stored value; a variant that never had one is 1000 g, so two variants
  are 1000 g each.
- **REQ-231** — A **new** variant (no id yet) shall not be saved without an
  explicit weight: the form starts it empty and required, and the save API
  refuses a missing weight with a stated 422 instead of inventing 1000 g.
- **REQ-232** — Saving an **existing** variant without a weight in the payload
  shall keep its stored weight, never reset it to 1000 g.
- **REQ-233** — The weight input shall state what it is for ("dipakai untuk
  ongkir Mengantar") and show the kg equivalent as the operator types
  (1250 → "1,25 kg").
- **REQ-234** — The order detail page (the invoice) shall show each item's unit
  weight and line weight and the order's total weight, in grams with kg, and
  say whose weight it is (see REQ-235).
- **REQ-235** — Until weight is recorded on the order, the page labels it as the
  variant's **current** weight, because that is what dispatch will send to
  Mengantar; it must not claim to be the weight that was quoted.
- **REQ-236** — The live fleet's weights shall be read once, read-only, and
  recorded: how many variants sit at the 1000 g default per store, so
  operators know which products to check.

### Technical decisions

- **Grams, never kg, in storage and input.** The column is already grams and the
  quote divides by 1000 in one place; the form shows kg only as a hint.
- **"Missing" and "1000" are different.** The parser returns null for a missing
  weight; a new variant with null is refused, and an update writes
  `weight_grams = COALESCE(?, weight_grams)`. The DB default stays for rows
  created by older code paths.
- **No upper bound is invented.** Mengantar's maximum parcel weight is not
  documented in this repository or its skill; the save keeps "positive
  integer" until that limit is verified from Mengantar's own documentation.
- **Snapshot is a proposal.** Recording `weight_grams` on `order_items` at
  checkout would make dispatch send exactly the quoted weight, but it changes
  the order write path, a protected surface. It is written up for Paduka's
  approval (A-397) and not done here.

## A40 — Cloudflare fit: stay inside what the plan allows

**Status:** Proposed 2026-10-29. Built from Cloudflare's own documentation and
practitioner reports, not from inference; every fact below carries its source.
Two items touch protected surfaces (TASKS, *Protected surfaces for A35–A43*) and
are therefore proposals only.

### Evidence

| # | Fact | Source | What it means here |
| --- | --- | --- | --- |
| E1 | Since **2026-09-01**, a Workers Free account over its daily D1 row-read (5M) or row-write (100k) allowance gets an error on **every** D1 query until 00:00 UTC. | [D1 changelog](https://developers.cloudflare.com/changelog/product/d1/), [D1 pricing](https://developers.cloudflare.com/d1/platform/pricing/) | The fleet runs on Workers Free (`STATUS.md`, `RELEASE.md` §cron). One install's spike stops checkout on every install in the account: the ADR-021 KV outage again, now in D1. |
| E2 | A full table scan counts every row it reads; indexes reduce rows read; each index adds one written row per write that touches its column. `meta.rows_read` reports it per query. | [D1 pricing](https://developers.cloudflare.com/d1/platform/pricing/), [Use indexes](https://developers.cloudflare.com/d1/best-practices/use-indexes/) | A37's reads must be measured, not assumed. Practitioners found their bills with `wrangler d1 insights` sorted by rows read, then `EXPLAIN QUERY PLAN` (Justin Ahinon, "I got a $134 Cloudflare D1 bill", 2026-04-25; Gary Wu, "cloudflare-cost-observability", garywu.github.io, 2026-04-28). |
| E3 | Every allowed call to a rate-limited public endpoint upserts a `rate_limits` row (`src/lib/rate-limit.ts`, the `INSERT … ON CONFLICT … RETURNING` after the read-first check). | Repo | `/api/locations` (each kecamatan search) and `/api/meta-event` (each browser event) spend D1 **writes**, the scarce Free resource under E1, across the whole account. |
| E4 | Workers Free: 10 ms CPU per request and per cron run; Paid: 30 s default. | [Workers limits](https://developers.cloudflare.com/workers/platform/limits/) | ADR-030 measured 80–220 ms CPU per request. How strictly the Free cap is enforced is not documented. |
| E5 | KV Free: 1,000 writes a day; over it, writes fail. | [KV pricing](https://developers.cloudflare.com/kv/platform/pricing/) | The hourly scheduler heartbeat still writes KV (`recordSchedulerRun`, 24 writes a day per install). |
| E6 | A **Workers Cache** hit returns the response without executing the Worker. Hits, and static assets once caching is on, are billed at the request rate. | [Workers Cache](https://developers.cloudflare.com/workers/cache/) | ADR-029 relies on the middleware still running on a cache hit to write the click-id cookie. Under Workers Cache it would not run, and ad attribution from cached landing pages would stop. |
| E7 | `ALTER TABLE … ADD COLUMN` may add only a VIRTUAL generated column, and generated columns can be indexed. D1 recommends `PRAGMA optimize` after creating an index. | [Generated columns](https://developers.cloudflare.com/d1/reference/generated-columns/), [SQL statements](https://developers.cloudflare.com/d1/sql-api/sql-statements/) | Confirms the A36 design and adds one statement to its migration. |
| E8 | D1 read replication is still public beta and works only through `withSession()`. Practitioners report replica lag (p95 ≈ 3.4 s) and a replica missing a just-migrated table. | [Read replication](https://developers.cloudflare.com/d1/best-practices/read-replication/), dev.to/riversea, "D1 read replicas returned stale data for 6 seconds" (year not shown) | Not for this product while the Worker already sits beside an APAC primary (ADR-030). |
| E9 | Practitioners converge on rollup or counter tables for dashboards, never `COUNT(*)` over raw tables per request or per minute. | Gary Wu, garywu.github.io, 2026-04-28; viblo.asia, 2026-10 | A37 stays live-aggregated only because it runs on an operator's click, inside a bounded range, under a measured ceiling. |

Not verified, so not relied on: whether the KV Free limit is per account (the
docs do not say; ADR-021's outage is the evidence), how a range scan plus table
lookups map onto `rows_read`, and whether Workers Cache hits count toward Free's
100k requests a day.

### Requirements

- **REQ-224** — Before any plan or architecture change, the account's daily D1
  rows read and written and KV writes over the last 30 days shall be read from
  the Cloudflare dashboard and recorded in `STATUS.md`.
- **REQ-225** — Workers Free versus Paid is Paduka's billing decision, recorded as
  an ADR with E1, E4 and the REQ-224 figures. The evidence points to Paid: on
  Free, one install's traffic can stop checkout on all of them.
- **REQ-226** — No work in A35–A40 adds a D1 or KV write to a storefront request.
- **REQ-227** — The `rate_limits` write cost (E3) shall be written up as options
  with their effect on writes: a Cloudflare WAF rate-limiting rule in front of
  the endpoint, counting only after a threshold, or a coarser window. It touches
  the form and tracking paths, so it is a proposal for Paduka, not a change.
- **REQ-228** — The scheduler heartbeat shall move from KV into the A39 D1
  snapshot, removing the last routine KV write (E5).
- **REQ-229** — Workers Cache shall not be adopted while server-side click-id
  capture depends on the middleware running for cached pages (E6). If it is
  wanted later, it needs an ADR that moves that capture first, under the
  tracking contract.

### Non-goals

- Read replication (E8), a second database, Durable Objects, or Analytics
  Engine. Each is a later ADR if a measured need appears.
- Changing the edge cache (ADR-029), Smart Placement or the cron schedule.

## A39 — Operational status beside the notification bell, with its own page

**Status:** Proposed. Replaces the "Kesehatan operasional" card on the dashboard.
`OBSERVABILITY.md` §4 item 4 owns what is measured; this changes where it is
shown and what it costs.

### Goals

- An owner or admin sees on every admin page whether anything needs attention,
  and one click explains why and where to fix it.
- The status page also answers "is my store set up", so setup and health are one
  place instead of two panels fighting for the dashboard.
- It costs no polling and at most one cached single-row read per page.

### Non-goals

- A public status page, paging, or a new alert channel. `OPS_ALERT_WEBHOOK_URL`
  and the hourly alert evaluation stay as `OBSERVABILITY.md` describes them.
- Changing the eight signals or their thresholds (`operational-health.ts`).
- A sidebar entry. The icon is the entry; the command palette also finds it.

### Requirements

- **REQ-216** — Owner and admin shall see a status icon beside the notification
  bell on every admin page. Other roles shall see none and send no request for it.
- **REQ-217** — The icon's state shall follow one precedence: **red with a count**
  when any signal is degraded or the check itself is stale; **amber** when a
  required setup step is left; **green** when every signal is healthy; **neutral**
  when nothing is known yet. "Belum ada data" alone is never red. The accessible
  name says it in words ("2 masalah operasional"); colour is never the only cue.
- **REQ-218** — The icon shall be a link to `/admin/status`, not a popover: one
  destination that works by keyboard and on a phone.
- **REQ-219** — `/admin/status` shall show the overall state, when it was checked
  and a **Periksa ulang** button; then **Perlu tindakan** (degraded signals, then
  required setup left), each with the plain-language cause, its numbers and an
  action; then **Setup toko** (the checklist the dashboard shows today); then
  **Semua sinyal** (the healthy and unknown rest, collapsed).
- **REQ-220** — Each signal shall offer its nearest fix as a button, from one map
  keyed by signal and reason: Meta CAPI → `/admin/ads/meta`, Google outbox →
  `/admin/ads/google`, a Mengantar or AutoLaris credential cause → Profil &
  Integrasi (`/admin/profile`, where both API keys live, as the setup checklist
  already links), an AutoLaris payment cause → `/admin/payments`. A cause that
  lives outside the admin shows what to do instead of a button that goes
  nowhere: the exact setting name, copyable, for `OPS_ALERT_WEBHOOK_URL` and
  `triggers.crons`, and "ask Mengantar CS for Receiver Score access" for
  `not-whitelisted`. A reason with no entry shows no button rather than a wrong
  one.
- **REQ-221** — The dashboard shall stop rendering the health card. While a
  required setup step is left it shall show one slim line linking to the page.
- **REQ-222** — The icon shall never report a stopped checker as healthy: a
  snapshot older than two hours is shown as a problem ("pemeliharaan berhenti").
- **REQ-223** — Checking from the page shall not send alerts or write alert
  state. Only the hourly run evaluates and sends them.

### Technical decisions

- **The hourly run writes the snapshot.** `scheduled()` already calls
  `collectOperationalHealth` every hour and logs it. It also upserts one row,
  `ops_health_snapshot` (`id = 1`: overall, degraded count, the signals as JSON,
  required-setup-left, `taken_at`). The icon reads that row; it never runs the
  eight-signal collection. Cost: one write an hour, one row read per page.
- **No polling.** The bell polls every 30 seconds (A19); the icon does not. It
  fetches `GET /api/admin/health/status` once on load, keeps the answer in
  `sessionStorage` for five minutes, and asks again on window focus. The
  endpoint answers `Cache-Control: private, max-age=60`. The fetch follows first
  paint, so it adds no latency to a page (ADR-030).
- **Staleness is a state.** If the cron stops, the snapshot stops changing and
  would read healthy forever. The read computes `now − taken_at`; over 120
  minutes it reports the stalled state itself, whatever the stored signals say.
- **Live check is a POST.** `POST /api/admin/health/check` runs the collection
  and the setup facts, writes the snapshot and returns it. It is a POST because
  it writes, so the middleware's same-origin check covers it. A snapshot younger
  than 15 seconds is returned as is, which is the whole rate limit.
- **`GET /api/admin/health` loses its side effect.** It currently also calls
  `evaluateOperationalAlerts`, which writes alert state to KV (ADR-021) and can
  fire the webhook, so every dashboard view could send one. After this change
  it only reads; the cron remains the one place that evaluates. Its tests move
  with it.
- **Setup is part of the snapshot.** `readSetupFacts` is several queries, so the
  icon's amber state reads the hourly count. The page recomputes it live; a store
  that has just finished a step sees the icon catch up within the hour or on
  **Periksa ulang**.
- **Reuse the component.** `OperationalHealth.tsx` already holds the reasons,
  age formatting and metric wording (259 lines). They move to the status page's
  island rather than being rewritten; the dashboard card is what is deleted.
- **The icon follows the bell's size and focus ring.** At 390px the top bar holds
  search, bell, status and profile; the check is that it does not overflow.

## A38 — Dashboard: best landing pages, best sellers and recent buyers

**Status:** Cancelled 2026-10-31 by the owner. Every panel repeats a screen the admin already has: Pembeli terbaru is the head of `/admin/orders`, and the landing-page and product rankings are Analitik. Kept as a record of
the design; not to be built without a new decision.

### Goals

- The dashboard answers, under the revenue trend and payment mix, *which landing
  page earns, what sells, and who just bought*, in three even columns.
- Opening the dashboard costs the same as today until the new row has loaded.

### Non-goals

- A per-panel period or settings. The row follows the dashboard's period; recent
  buyers is always the latest.
- Buyer contact data on the dashboard (phone, address). The order page owns it.
- Replacing the Analitik menu: each panel links to it.

### Requirements

- **REQ-209** — Below the trend and payment-mix row, three equal panels:
  **Landing page terbaik**, **Produk terlaris**, **Pembeli terbaru**. One column
  on a phone, two at `lg`, three at `xl`, equal heights, rows at a touch-friendly
  size.
- **REQ-210** — Landing page terbaik lists the top 5 sources by delivered revenue
  for the dashboard's period, each with orders and revenue and a thin bar scaled
  to the leader. Produk terlaris lists the top 5 by units, with revenue. Each
  panel ends with a link to the matching Analitik screen carrying the same period.
- **REQ-211** — Pembeli terbaru lists the 8 latest orders, leads excluded: the
  buyer's first name and an initial, city, the first product with "+N lainnya",
  the amount, a relative time and the status chip. A row opens that order. No
  phone and no address are sent to the browser for this panel.
- **REQ-212** — Panels follow the role: owner and admin see all three; advertiser
  sees the first two (that role cannot open orders); customer service sees only
  Pembeli terbaru. A panel a role may not see is neither requested nor drawn, and
  the endpoint refuses it with 403 rather than returning an empty list.
- **REQ-213** — One request returns every panel the caller may see, from one
  `D1.batch`. Each panel has a skeleton of its final size and an empty state that
  names what is missing ("Belum ada pesanan bersumber landing page").
- **REQ-214** — The row loads after the KPI cards and chart are drawn and does not
  delay them.
- **REQ-215** — A source with no record appears as `(tidak tercatat)` as in A37,
  and the panel's numbers equal the Analitik screen's for the same period.

### Technical decisions

- **One endpoint, sections by role.** `GET /api/admin/dashboard-panels?sections=…`

  handler checks each

- **Recent buyers is two bounded reads.** The latest 8 non-abandoned orders by

### Technical decisions

- **Weight is the design constraint.** Everything is a `GROUP BY` over `orders`
  inside a bounded `created_at` range, which the existing
  `idx_orders_created_at` serves. A screen costs about *(rows in range) × (its
  query count)* D1 rows read, a product screen adds `order_items`. Each API
  returns D1's `meta.rows_read` in a header during development and a test
  asserts a ceiling against a seeded fixture, so a later query that scans the
  table fails loudly.
- **One route, one API, one batch per screen.** Separate routes keep a tab the
  operator never opens from costing a read. Each API runs its queries in a
  single `D1.batch`, no N+1, no per-row lookups; names for landing and product
  are joined in the same batch.
- **Admin responses are not cached.** `Cache-Control: no-store`, matching the
  existing session-aware middleware. The original browser-cache proposal was
  never effective through that middleware; this feature does not weaken its
  revocation boundary. No KV write (ADR-021) or edge cache (ADR-029).
- **Aggregate in SQL, shape in `src/lib`.** SQL returns grouped rows; a pure
  module turns them into the series, the top-N plus `Lainnya`, and the
  zero-filled days (the dashboard already zero-fills in the route). The module
  is what the test runner reaches; the React island only draws.
- **Charts reuse what is installed.** `recharts` and the shadcn `chart.tsx`
  already ship; no new library. Each screen is a lazily loaded
  `client:only` island, so a screen's chart code loads only when opened. A new
  data island is added to `admin-islands-render.test.ts` or its logic stays in
  `src/lib`.
- **Shared definition.** `RELEASED_ORDER` lives in `src/lib/order-metrics.ts`.
  Both the existing dashboard and the new insights import it, so
  the dashboard card and this menu cannot drift.
- **Role prefix trap.** `canAccessAdminRoute` matches a role's route entry as a
  prefix (`matchesRoute`: equal, or `startsWith(route + '/')`), and
  `customer_service` holds `/api/admin/analytics`. An endpoint added beneath that
  path would be open to customer service the moment it exists. The new endpoints
  therefore use `/api/admin/insights/*`. Only owner passes every route; admin is
  held to `ADMIN_API_ROUTES` and `ADMIN_PAGE_ROUTES`. So the endpoint prefix goes
  into the admin and advertiser API lists, and `/admin/analytics` into the admin
  and advertiser page lists. A test asserts customer service gets a 403 on every
  one.
- **Timezone.** The dashboard converts with a literal `'+7 hours'`. This menu
  reuses that exact expression, not a second one.

## A36 — Know where a lead came from

**Status:** Proposed. Smallest slice that A37 stands on.

### Goals

- Every order and every lead says which landing page it came from, as a short
  slug, visible where the operator already works.

### Non-goals

- Full URLs, query strings or domains: the last path segment only.
- First-touch versus last-touch modelling. An order keeps the page it was
  submitted on; a lead keeps the page it was captured on.
- UTM campaign reports. The channel split (REQ-203) reads what the order already
  holds; A36 adds no tracking parameter.

### Requirements

- **REQ-191** — Each order and lead shall carry a `source_slug`: the last path
  segment of the page it was submitted from, lower-cased, without query, hash or
  trailing slash, at most 80 characters. The home page is `beranda`; a path with
  no usable segment is null.
- **REQ-192** — A lead (an abandoned-checkout capture) shall record its source
  when captured. Today only a completed order stores `source_page_path`; the
  lead endpoint ignores it, so a lead's origin is lost.
- **REQ-193** — Existing orders shall have a slug without a backfill and new
  orders without any change to how an order is written; rows without a path stay
  null and read as `(tidak tercatat)`.
- **REQ-194** — The order list and the abandoned-lead list shall show the source
  slug as a column, with the full path as its tooltip, and shall filter by it.
  The filter lists the slugs actually present, most frequent first. The slug is
  a short chip beside the existing traffic-source badge, truncated with the full
  path in its tooltip, so the list gains no column and a phone card gains one
  chip rather than a line.
- **REQ-195** — The slug shall be shown with what it is when it is known: a CMS
  landing page by its title, a native page by its registered name, a product page
  by its product, otherwise the bare slug.
- **REQ-196** — Order detail keeps showing the full recorded path; the slug is
  derived from it, never entered by hand.

### Technical decisions

- **A computed column, so the order flow is not touched.** `source_slug` is
  `GENERATED ALWAYS AS (…) VIRTUAL` over `source_page_path`, with
  `INDEX (source_slug, created_at)` for the filter and the A37 ranking. SQLite
  computes it for old and new rows alike, so no submit route, `persistOrder`
  statement or backfill changes. Proven in plain SQLite on 2026-10-29; D1 must
  be proven on local D1 before merge, and if it refuses, the fallback is brought
  back for a decision rather than taken.
- **One definition, two readers.** The SQL expression is the definition; a pure
  `sourceSlugFromPath` mirrors it for labels and tests, and a test feeds both
  the same paths so they agree.
- **A lead's page comes from `Referer`, not from the form.** The form's `fetch`
  to `/api/record-abandoned-order` is same-origin and the store sends
  `Referrer-Policy: strict-origin-when-cross-origin`, so the header holds the full
  page URL. The route takes its pathname, so the three form scripts stay as
  they are. The lead upsert gains one bound column; the order statements do not.
- **A landing served as a product page** submits from `/produk/<slug>`; its slug
  is the product page's. The label step (REQ-195) resolves it, so the operator
  sees one page, not two names.
- **The client supplies the path** (`window.location.pathname` for an order,
  the `Referer` header for a lead), so it is untrusted: it is clipped,
  normalised, and used only as a label and a group key, never as a URL or in
  markup unescaped.

**Status:** Proposed. Builds on A28; changes which number A28 hands the buyer to.

### Goals

- A store lists several support WhatsApp numbers and `/thanks` hands each COD
  buyer to one of them, evenly: two active numbers about 50:50, three about

  order and breaks REQ-187).

### Requirements

- **REQ-184** — An operator shall manage the numbers in their own admin menu:
  add (label optional, number required), edit, activate and deactivate, remove.
  A number is normalized to `62…`, must be usable by the `wa.me` rule
  (`thanksWhatsappUrl`), must be unique, and at most 10 are kept.
- **REQ-185** — At least one number shall stay active. Deactivating or removing
  the last active one is refused with a stated reason. A store whose list is
  empty falls back to `stores.support_whatsapp`, and `/thanks` loses its button
  only when that is empty too, as today.
- **REQ-186** — With *n* active numbers, `/thanks` shall assign each order to one
  uniformly: 1 → 100%, 2 → 50% each, 3 → 33.3% each. The admin page shall show

- **REQ-187** — The same order shall always get the same number: reload, return
  from the payment page and reopening the page do not change it.
- **REQ-188** — The assigned number shall be used by the confirm button and the
  automatic hand-off alike; the message (REQ-183) and the redirect timing
  (REQ-182) do not change.
- **REQ-189** — An existing store shall keep its number as the first list entry
  after upgrade with no operator action, and a fresh install shall start with
  the number it was given. `stores.support_whatsapp` shall mirror the first
  active number so the surfaces outside this scope read the same value.
- **REQ-190** — The order-form submit time and the Mengantar kecamatan
  resolution shall be measured and reported, read-only. Any change either would
  need is in the order path, which A35–A39 do not touch (TASKS, *Protected
  surfaces*); it is proposed one finding at a time and made only on Paduka's
  approval.

### Technical decisions

- **Pick in the browser, from the order number.** `/thanks` learns the order
  number client-side (the query string is stripped by a 303 and the value lives
  in `sessionStorage`), so the server cannot hash it. The server ships the
  active numbers; a pure function in `thanks-whatsapp.ts` picks
  `fnv1a(orderNumber) mod n`. No write, no counter, no cache change: `/thanks`
  is already `no-store`.
- **"50:50" is statistical.** A hash is uniform over many orders; ten orders will

  invoice numbers inside a measured tolerance, not an exact split. The index

- **Settings → Store stops owning the number.** Its field becomes a link to the
  new menu; the A28 on/off switch stays there. The store PUT must not clear
  `support_whatsapp` when the field is absent.
- **Numbers the `wa.me` rule rejects** (a legacy foreign number, say) are
  filtered out at pick time rather than producing a dead link.

## A27 — Bounded landing-page content and images

**Status:** Accepted — shipped (migration `0055`, typed sections in the editor and renderer; A-174 … A-185).

### Goals

- Let an operator compose a CMS landing page without writing HTML for the common
  text and image sections.
- Keep image processing in the browser and object storage, so upload conversion
  cannot consume Cloudflare Worker CPU.
- Render every supported image at its natural aspect ratio within the existing
  responsive landing column.


### Visual builder UX

- **Actor and permission:** authenticated `owner`, `admin`, and `advertiser`
  compose their store's CMS landing pages; only `owner` and `admin` retain the
  existing product-page claim action.
- **Primary flow:** select **Tambah section**, choose one bounded type, edit its
  named fields in the selected section card, use the numbered canvas navigator
  or existing up/down controls to reach and order it, then save the page. The
  480px storefront canvas is the primary live preview, not a separate editor or
  a pixel-positioning workspace.
- **Section cards:** retain the numbered header and selected blue ring. The
  navigator shall focus and smoothly reveal the selected card in a long canvas.
  Type labels/icons and controls remain labelled; first/last movement disables
  correctly. Text fields edit in place. Lists use one item per row, with explicit
  add/remove item controls. Image cards show upload progress, preview, alt-text
  input, deterministic rejection reason, and retry without discarding the
  current section.
- **Responsive and accessible behavior:** at desktop, keep configuration beside
  the 480px preview; below `lg`, stack configuration before the canvas. Every
  input has a visible label, errors are adjacent to the affected field, icon
  actions have accessible names, focus remains in the edited card after adding
  or removing an item, and no drag-only interaction is required.
- **States:** an empty canvas offers the bounded section choices; an upload
  pending state disables only that image card's upload action; failed conversion
  or upload keeps the source configuration and offers retry; saving does not
  discard unsaved input on a recoverable request error.

### Non-goals

- A free-form visual canvas, rich-text editor, arbitrary CSS, arbitrary HTML,
  video, carousel, gallery, image cropper, or drag-and-drop asset library.
- Server-side image decoding, resizing, or format conversion; Cloudflare Images,
  Workers AI, a queue, and a new image dependency.
- A claim that every file named or declared as an image is convertible. SVG,
  animated images, HEIC, and any type the operator's browser cannot decode are
  rejected rather than uploaded or silently changed.
- Changing existing `html` and `form` section behavior or rewriting existing
  R2 objects.

### Requirements

- **REQ-173** — The system shall support ordered CMS landing sections of type
  `headline`, `paragraph`, `numbered_list`, `bullet_list`, and `image`, in
  addition to the existing `html` and `form` types; each new type shall persist
  only its typed plain-text or image configuration, never generated HTML.
- **REQ-174** — When an operator adds or edits a new text or list section, the
  admin shall provide named plain-text controls, preserve the landing page's
  existing section order and draft state, and reject an empty required value or
  malformed typed configuration before replacing the stored sections.
- **REQ-175** — When an operator selects a landing image no larger than 2 MiB,
  the browser shall decode a supported static raster image, resize it to the
  existing image-edge budget, encode it as WebP, and upload only a WebP no
  larger than 2 MiB; if decoding or encoding fails, or either size limit is
  exceeded, then the upload shall fail without an R2 write.
- **REQ-176** — The image upload endpoint shall accept a landing image only as
  a signature-validated WebP under 2 MiB, retain the existing authenticated
  rate-limit boundary, and return an install-local `/assets/uploads/...webp`
  URL; it shall not trust a file extension or browser MIME declaration alone.

- **REQ-177** — The public landing route shall render the new section types as
  semantic text, list, and image elements; images shall be fluid
  (`max-width: 100%`, automatic height), retain their intrinsic aspect ratio,
  avoid forced cropping, lazy-load below the fold, and never cause horizontal
  page overflow at supported widths.
- **REQ-178** — Existing `html` and `form` landing sections and their URLs,
  previews, shortcodes, product-page claims, and draft/published behavior shall
  remain unchanged; malformed new-section data shall fail safely without
  rendering raw markup or another product's asset.
- **REQ-179** — When an operator edits a `headline`, the admin shall offer
  left, center, and right alignment plus small, medium, and large text-size
  choices. A `paragraph` shall offer alignment and render as the standard body
  style. Valid selections shall persist in typed section configuration and
  render consistently in the preview and public landing route. New and legacy
  text configurations shall default to left alignment, medium headline size,
  and body paragraph style.

### Technical decisions

- **Browser Canvas encoding, not Worker conversion.** The repository already
  has `client-image.ts` and browser-side WebP encoding. Bounding the original
  file at 2 MiB keeps Canvas memory bounded while R2 receives one small object;
  the Worker only validates bytes and performs one R2 `put`.
- **Typed JSON configuration, not HTML synthesis.** A new nullable JSON
  configuration column avoids HTML as a storage format for plain text and lists,
  while preserving `content_html` for legacy sections. The type CHECK change
  needs a forward migration that rebuilds `landing_sections` and copies every
  current row unchanged.
- **Browser-decodable static raster is the honest boundary.** “All image
  formats” is not portable: Canvas can only encode images the current browser
  decodes, and animated or vector inputs cannot become one equivalent WebP.
  The UI must state this boundary and reject unsupported files before upload.
- **Local HTTP compatibility.** The admin builder shall not require
  `crypto.randomUUID()` in browser code: a Tailscale HTTP origin is not a
  secure context and does not expose that method. Transient unsaved-section
  identifiers may use a timestamp/random fallback because D1 assigns the
  durable identifier on save.

## A22 — Release-driven updates for isolated installs

**Status:** Accepted, **revised 2026-08-23 per ADR-020** — updates are
distributed by manual copy, not a fleet engine. Security gate A-151 is done; the
engine requirements (REQ-165/166/168/169/171) are withdrawn as YAGNI. Pre-
remediation evidence is in `docs/AUDIT-2026-08-23.md`; open execution is owned by
`TASKS.md` A-151 (done), A-153 (manifest), A-159 (optional).

### Goals

- Update every installation from one tested AdsBookCMS release by copying the
  product-owned paths into its own repo, guided by a path-ownership manifest so
  install-owned config is never overwritten.
- Preserve the existing isolation boundary: one repository, Worker, D1, KV, R2,
  domain, and credential set per store.
- Make every proposed installation update reviewable, reproducible, and
  attributable to an immutable product revision.

### Non-goals

- A multi-tenant Worker, shared D1 database, tenant router, provisioning control
  plane, or shared runtime credential store.
- Copying customer, order, payment, catalog, or analytics data between installs.
- Deploying every production store automatically when product `main` changes.
- Replacing each installation repository with generated or unreviewable state.
- A package registry, GitHub App, queue, fleet updater, or hosted fleet service
  (ADR-020).

### Requirements

- **REQ-164** — Before a product release is eligible for installation, every
  inline raw-text JSON payload shall escape HTML script terminators, and a
  regression test containing a literal `</script>` payload shall prove it.
- **REQ-167** — The updater shall leave install-owned configuration, Cloudflare
  resource identifiers, secrets, merchant assets, and local operational records
  unchanged; an unclassified changed path shall fail the update before writing.
- **REQ-170** — Each installation shall retain its own database and apply only
  the product's ordered forward migration suffix; no fleet command shall read or
  copy customer rows between D1 databases.
- **REQ-172** — Local product development shall use one canonical `main`
  worktree plus task-named temporary worktrees; a generic persistent detached
  worktree shall not be treated as a current development environment.

> **Revision 2026-08-23 (ADR-020).** REQ-164 is met. REQ-167 and REQ-170 are
> satisfied by the path-ownership manifest plus the per-install migration
> contract — a checklist, not an automated updater. REQ-172 is worktree hygiene.
> The fleet-updater requirements (REQ-165/166/168/169/171) were withdrawn as
> YAGNI and removed from this document on 2026-09-25.

### Technical decisions

- **Git release, not a package.** Installations already contain the complete
  Worker and migration chain; a Git revision is the smallest artifact that
  preserves deletions, migration history, and source provenance.
- **Classified copy, not blind overwrite.** Every changed path is product-owned
  or install-owned (`docs/UPDATE-PATH-OWNERSHIP.md`); an unknown path stops the
  update before anything is written.
- **Review before production.** Merge and deploy remain installation-owned
  actions behind the existing production approval gate.

## A21 — A landing page may become the product page

### Goals

- One product can be sold through a purpose-built landing page without that page becoming a second competing URL.
- The operator decides it from the landing-page list, and can undo it.

### Non-goals

- *(Superseded.)* Native Astro landing routes were first out of scope here. The
  native register (`src/data/native-landing-pages.ts`) now records them in
  `landing_pages`, so the CMS lists them and a registered native page can serve
  its product's page like a CMS page; see `docs/LANDING-PAGES.md`.

### Requirements

- **REQ-159** — An operator shall be able to make one active CMS landing page serve its product's page, and to release it again.
- **REQ-160** — Where a landing page serves the product page, `/produk/<product-slug>` shall render it and be its canonical address, and the landing page's own slug shall permanently redirect there (`301`, cacheable for five minutes, query string kept), so exactly one URL is live.
- **REQ-161** — At most one landing page may serve a given product's page, enforced by the database rather than by the interface.
- **REQ-162** — If the claiming landing page becomes inactive or releases the claim, then `/produk/<product-slug>` shall return to the standard product template; a product shall never 404 because a landing page changed.
- **REQ-163** — Every landing page, CMS or native, shall answer at `domain/<slug>` with no path prefix, except where `REQ-160` moves it to the product URL.

### Technical decisions

- **The product route hands off by rewrite, signalled on the request.** A rewrite does not carry the original path, so the landing route cannot tell a hand-off from a direct visit by reading `Astro.url` — doing so put the two routes in an endless redirect loop. An `x-adsbook-product-page` header carries the fact instead.
- **A partial unique index, not application logic.** `WHERE is_product_page = 1` leaves unclaimed drafts out of the index entirely, so any number may target one product while only one may hold it.
- **Copy stays historical, navigation stays live.** The admin list builds its link from the product slug when a page is claimed, so an operator never copies an address that merely redirects.

## A20 — One date-range control across every reporting surface

### Goals

- An operator picks a reporting period the same way on the dashboard, the order list, and the shipping workspace.
- A period can be an explicit start and end date, not only a named preset.

### Non-goals

- A new date-picker dependency. The platform's own `<input type="date">` already renders a real calendar, and on a phone it renders the OS picker, which beats any in-page grid.
- Per-surface period semantics. One resolver already exists (`admin-date-filter.ts`); this phase extends it rather than growing a second.

### Requirements

- **REQ-154** — The dashboard, order list, and shipping workspace shall present one shared period control offering the same presets plus an explicit custom range.
- **REQ-155** — A custom range shall be expressed as an inclusive start and end date in Asia/Jakarta, and shall be rejected — not silently reinterpreted — when the start is after the end, either date is unparseable, or the span exceeds that surface's documented maximum.
- **REQ-156** — Where a surface caps how much history it can report on, the control shall state the cap and prevent selecting past it rather than truncating the answer silently.
- **REQ-157** — A request naming a period the server cannot resolve shall be refused with a stated reason; it shall not fall back to a different period and present the result as the one that was asked for.
- **REQ-158** — The active period shall be legible without opening the control, including which custom dates are in force.

### Technical decisions

- **`<input type="date">`, not a calendar library.** It is a real date picker, it is the native one on mobile, it needs no bundle, and the repository currently carries no date dependency at all. A two-month drag-select grid would be the only reason to add one, and no requirement here asks for that.
- **One resolver, extended.** `resolveAdminDateRange` gains an optional custom range and a validating parser shared by all three APIs, because two of them currently pass an unvalidated string into a typed parameter and silently receive the 7-day default for anything unrecognised — including `custom`.
- **The cap stays per surface.** The dashboard already limits custom ranges to 30 days and hides the 90/180-day presets; the order and shipping lists do not have that constraint. The control takes the cap as input rather than imposing one number on surfaces with different costs.

## A19 — Operator notifications for revenue events

### Goals

- An operator learns that an order arrived, a lead was left behind, or a payment cleared without watching the dashboard.
- Notification state is server-owned and per-install, so it survives a reload, a second device, and a different browser.
- No third-party messaging account, credential, or per-message cost is introduced.

### Non-goals

- Outbound messaging channels (WhatsApp gateway, Telegram, email). They carry a per-install credential and, for WhatsApp, a per-message cost; none is required to solve "the operator did not notice".
- Customer-facing notifications. This phase is operator-only.
- Delivery while no admin page is open anywhere. That needs Web Push and is specified as REQ-153, deliberately deferred rather than implied.

### Requirements

- **REQ-146** — When a checkout creates an order, the system shall record exactly one `order` notification for that order, and a repeated or replayed write shall not produce a second one.
- **REQ-147** — When a qualified missed-order lead is captured, the system shall record exactly one `lead` notification for that lead.
- **REQ-148** — When an order's payment becomes paid, the system shall record exactly one `payment` notification for that order, whichever confirmation path set it.
- **REQ-149** — Notification recording shall never fail, delay, or roll back the commerce write that triggered it; a notification store that is unavailable shall be logged and skipped, not surfaced to the buyer.
- **REQ-150** — The system shall expose to an authenticated operator an unread count and a reverse-chronological notification list scoped to roles that own commerce work; `advertiser` shall not receive commerce notifications.
- **REQ-151** — An operator shall be able to mark one notification read and to mark all read; read state shall be per operator, so one operator reading does not blind another.
- **REQ-152** — Where an admin page is open and the browser has granted permission, the system shall raise a browser notification for an unread event at most once per event per browser, and the absence or denial of that permission shall degrade to the in-app list without an error state.
- **REQ-153** *(Planned)* — Where no admin page is open, the system shall deliver the same events through Web Push using VAPID and a service worker. On iOS this requires the operator to install the admin to the home screen first, a platform restriction that shall be stated in the operator UI rather than silently failing.

### Technical decisions

- **D1, not KV, for the notification store.** The feature needs ordering, an unread count, and per-operator read state — all queries. KV holds the alert-transition state in `operational-alerts.ts` because that is one value per signal; this is a list.
- **Polling, not SSE or WebSocket.** An open SSE stream pins a Worker isolate per open admin tab for as long as it stays open. The admin page is already loaded and already makes requests; a bounded poll on an open page costs less and cannot leak isolates.
- **Recording is inline with the commerce write, wrapped fail-open.** A queue would need its own delivery guarantee to solve a problem the write itself already orders correctly. REQ-149 makes the failure mode explicit instead.
- **Dedupe is a stored uniqueness constraint keyed by event type plus subject id**, the same discipline the CAPI outbox uses for `event_id` — retries and replays are expected, so exactly-once is enforced by the store rather than by the caller remembering.

## A18 — Deterministic storefront home and structured content editor

### Goals

- Make the public homepage automatically index active products and published landing pages.
- Replace JSON/AI homepage authoring with bounded banner, slider, and supporting-copy fields.

### Non-goals

- Runtime discovery of arbitrary `.astro` files, raw HTML/JSON authoring, Workers AI generation, or deleting existing landing URLs.

### Requirements

- **REQ-140** — The system shall render the public homepage with the canonical `compact-market` composition only; a stored alternate template shall not change homepage layout.
- **REQ-141** — When a product is active and has a sellable variant, the system shall include it in the homepage catalog automatically, newest first, in a two-column grid with ten items initially visible and an accessible Load more control for remaining items.
- **REQ-142** — When a CMS landing page is active, the system shall include its title, safe summary, and canonical public URL in the homepage landing-page index and sitemap without a separate homepage publish action.

## 0. About this document

AdsBookCMS is a direct-response commerce CMS that installs onto Cloudflare Workers. **One installer run produces one Worker, one database, one store.**

The previous version of this document specified a multi-tenant engine with a provisioning installer, a tenant registry, and fleet deployment — none of which exists in this repository. It also defined three requirement IDs twice with different text, and mandated behaviour (`admin`/`admin` login) that the code was deliberately hardened against.

Requirement numbering therefore **restarts** here. The old `REQ-*`, `SEC-*`, `PAY-*`, `ORD-*`, `TRK-*`, `UI-*` identifiers referenced by `TASKS.md` do not resolve to this document and should not be reintroduced.

Each requirement carries a status:

- **Implemented** — covered by the last executed repository baseline or later evidence named in the row
- **Partial** — works, with a stated limitation
- **Accepted** — decided product behavior; the row states whether source is visible, while execution remains unclaimed until evidence exists
- **Planned** — decided backlog behavior not yet built

---

## 1. Product definition

AdsBookCMS gives one merchant a complete direct-response storefront: catalog, landing pages, checkout with cash-on-delivery and online payment, order and shipping operations against an Indonesian 3PL aggregator, ad-signal tracking for Meta and Google, and an admin dashboard — deployed as a single Cloudflare Worker the merchant owns.

**Goals**
1. A merchant can install, configure, and operate a store without a developer after the first deploy.
2. The install is isolated: its own Worker, database, media bucket, domain, and credentials.
3. Commerce truth is server-side. Browser state never determines price, stock, or eligibility.
4. Ad platforms receive accurate, deduplicated conversion signals.

**Non-goals**
1. Multi-store operation inside one Worker (ADR-001).
2. Customer-authored code or a plugin runtime. First-party plugins compiled into
   the product and activated per store (ADR-028) are not this.
3. Public self-service signup.
4. Marketplace features — multi-seller, bidding, escrow.

## Operator payment switch on the admin order (REQ-250)

- **REQ-250** — An owner, admin or customer-service operator shall be able to
  move a COD order to a prepaid method from the admin order page when the
  buyer asks to pay first: manual transfer to an active seller account, or an
  AutoLaris VA/QRIS channel the store has live (the same readiness
  `/api/payment-methods` reports). One direction only; there is no buyer-side
  switch. The switch is refused unless the order is pending, unpaid, not
  void, not dispatched or being dispatched, and carries a real courier (not
  the `ICO` placeholder), a destination area and a kecamatan; otherwise the
  page says why. The prepaid total is items − discount + shipping, the COD fee
  dropped; a VA/QRIS admin fee follows the store's fee bearer exactly as at
  checkout. The write is guarded on every precondition and the read total, so
  a concurrent dispatch or edit wins. A provider failure after the switch
  leaves a prepaid order with a failed instruction the buyer can regenerate
  from `/payment`. The order records `payment_switched_from/_at/_by`. An
  unpaid prepaid order offers "Salin link pembayaran" (the buyer's `/payment`
  page) for the operator to send. When the order was already pushed to Kelola
  (which answers a resend as a duplicate and has no update route) the page
  tells the operator to correct it there by hand. The COD Purchase already
  sent keeps its event id (the order number), so the paid Purchase that
  follows deduplicates against it.

## A45 — Operations API and `adsbook` CLI, beside the storefront headless API

**Status:** Accepted 2026-10-30 (Paduka: "lanjutkan development task yang
belum"). Revised the same day: the storefront headless API stays (Paduka:
"headless tidak perlu di hapus"), so A45 adds an operations API beside it and
retires nothing; A-432 and A-433 are cancelled. Supersedes the A36 non-goal
"UTM campaign reports".

### Overview

Operators, the owner's own systems (Kelola, scripts), AI agents and named third
parties need to read and act on a store's orders without a browser session.
Today the only machine surface is `/api/v1`, built for a headless storefront
(catalogue, quote, checkout, tracking, token-scoped order status). Its
foundation — hashed per-install keys (`developer_api_keys`), scopes, per-key
rate limit and daily quota, and a D1 audit trail (`headless_api_audit_events`,
`developer_api_key_usage`) — is reusable; its endpoints serve a storefront,
not operations.

A45 builds an operations API on that foundation under its own prefix,
`/api/ops/v1`, with its own `ops:` scopes, and leaves the storefront contract
(`STOREFRONT_INTEGRATION.md` §4) as it is, plus an `adsbook` CLI in this repository that is a thin
client of the same API. It also turns the UTM tags every order already stores
(`orders.ad_click_ids`, TRACKING_SPECS §3) into a campaign report and a link
builder.

The same CLI carries the native Astro landing page workflow
(`docs/LANDING-PAGES.md`, `docs/NATIVE_LANDING_PAGE_SPEC.md`) into the install
repository where those pages are written: `adsbook lp new` scaffolds a page that
passes the suite on its first build, and `adsbook lp check` decides every item
of the spec's checklist a machine can decide, asking the store over the API
whether the product is live and the slug is free. Building and deploying stay
the install's own release path; the CLI never does either.

### Users and current workaround

| Role | Job to be done | Current workaround |
| --- | --- | --- |
| Owner / operator | Check and act on orders from a terminal or script | Admin pages only, one order at a time |
| Owner's systems (Kelola, scripts) | Pull new or changed orders; react to paid/shipped | Kelola gets a one-shot push at creation; nothing else |
| AI agent (Claude, Codex) | Answer "which orders are stuck", act on request | Scrapes nothing; asks the operator |
| Third party (agency, partner) | Read orders and campaign results for one store | Screenshots and spreadsheets from the owner |
| Advertiser role | Compare campaigns by UTM | Channel split only (REQ-203); no campaign level |
| Developer / AI terminal in an install repo | Ship a native landing page that sells one product | Copies `contoh-landing.astro` by hand, reads the spec's checklist, checks `/admin/landing-pages` for the slug by eye |

### Goals

- Every order an operator can see in admin is readable by a key with the
  matching scope, with its attribution (source slug, traffic source, UTM).
- An order action taken through the API or CLI obeys exactly the rules the
  admin page obeys, because it calls the same code.
- A campaign's orders, revenue and closing rate are visible per UTM tag, and
  links carrying those tags are built consistently.
- A storefront key never reads or acts on operations data, and an operations
  key never reaches a storefront route, whatever the key's age.
- A native landing page starts from a scaffold that already obeys the tracking,
  catalogue-identity and form-mode invariants, is checked against the live
  store before it ships, and survives every install update.

### Success measure

Read once A45's v1 milestone ships on one live install:
- the owner's Kelola/script integration pulls orders through `updated_since`
  instead of relying on the creation push alone;
- the UTM report attributes ≥ 90% of orders that carry any `utm_campaign`
  to a named campaign row (the rest are malformed tags, reported as such);
- the next native landing page built in an install passes `npm test`,
  `npm run check` and `npm run build` with no edit to scaffold-generated
  structure, and `adsbook lp check` reports no failure before its deploy.

### Non-goals

- A buyer-facing or storefront API. Checkout stays the install's own forms.
- Multi-store keys or a cross-install fleet API: one key belongs to one install
  (1 installer = 1 Worker = 1 store).
- OAuth, per-user tokens or a developer portal. Keys are issued by the owner in
  admin.
- Product, page or settings writes through the API.
- A published npm package for the CLI (in-repo first; revisit if a third party
  needs it).
- Visit counts or conversion rate against sessions (PRD A37 deferral stands).
- Changing how UTM tags are captured or merged (TRACKING_SPECS §3 owns that).
- The CLI building, previewing on a live store, or deploying a landing page,
  or writing a landing page through the API. A native page is application code
  released from the install repository (NATIVE_LANDING_PAGE_SPEC §7).
- Generating landing page copy, claims or imagery. The scaffold writes the
  structure; the sections and their evidence are the author's.
- Converting a CMS landing page into a native one, or the reverse.

### Stack & constraints

- Astro endpoints on the Worker; D1 only; no new dependency (CLI on `node:`
  built-ins and `fetch`). The CLI uses `fetch`; `src/lib/headless-client.ts` stays the storefront's client.
- One install = one store: a key is bound to its install, so tenant isolation
  is the install boundary; no store id is accepted from the client.
- `adsbook lp` writes only inside the working tree it runs in, only the three
  paths REQ-266 names, never overwrites, and touches no Cloudflare resource.
  Its template and checks live in `src/lib`, so they reach installs with the
  product and are covered by `npm test`; `scripts/adsbook.ts` stays a thin
  argument parser.
- The D1 budget (PRD A40) applies: list and report queries are bounded by
  period or cursor and measured with `rows_read` before acceptance.
- PII: third-party keys are issued without `ops:orders:read_pii` by default in the
  UI; buyer data never appears in logs or audit rows.

### Technical decisions

- **Decision:** extend the existing key/scope/audit foundation rather than add
  a second auth system. **Why:** hashed keys, quotas and audit already exist
  and are tested (`headless-api.test.ts`, `developer-api-keys.test.ts`).
  **Consequence:** operations scopes are namespaced `ops:`; old keys keep their
  storefront scopes and gain none (REQ-252), so the owner issues an operations
  key.
- **Decision:** the API calls the admin's own library functions for every
  action. **Why:** one rule set; AGENTS.md §3 forbids order writes around
  `order-lifecycle.ts`. **Consequence:** an action missing a library entry
  point gets one extracted from its admin route first.
- **Decision (revised 2026-10-30):** operations routes under `/api/ops/v1`.
  **Why:** the storefront API stays at `/api/v1` with its origin allowlist and
  CORS, built for browsers; operations calls are server-to-server and must
  inherit neither, and `/api/v1/orders/status` is taken. **Consequence:** two
  OpenAPI documents, one per surface.
- **Decision (revised 2026-10-30):** the storefront contract is not retired;
  REQ-107's headless surface and STOREFRONT_INTEGRATION §4 stand.
- **Decision:** the scaffold is a template in `src/lib`, not a copy of
  `contoh-landing.astro` at run time. **Why:** the sample binds to the first
  active product and is `noindex` on purpose; a real page names its product
  and is indexable. **Consequence:** the sample and the template are both run
  through `lp check` in `npm test`, so neither drifts from the invariants.
- **Decision:** register entries are created `isActive: false`. **Why:** the
  CMS lists and links an active entry as soon as it deploys; the author flips
  it when the page is proven. **Consequence:** `lp check` warns on an inactive
  entry so it is not forgotten.
